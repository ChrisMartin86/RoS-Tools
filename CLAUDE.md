# CLAUDE.md

Guidance for Claude Code when working in this repository.

## What this is

`RoS-Tools` — a World of Warcraft **retail** addon (Interface 120000) that shows
guild members' item levels from a static data file generated by a Blizzard
Community API export. The addon never calls out to the internet; it reads
`Data/GuildData.lua`, which is regenerated out-of-band by
`Tools/fetch_guild_info.py`.

Two languages, cleanly split:

- **Lua 5.1** — everything under `Core/`, `Modules/`, `Data/`. Ships to users.
- **Python 3** — `Tools/` only. Development-only; excluded from the packaged zip.

## Hard constraints

- **WoW runs Lua 5.1.** No `\u{}` escapes, no `//` integer division, no `goto`,
  no bitwise operators, no `#!` on tables. Raw UTF-8 bytes must be spelled out
  (see `RIGHT_SQUOTE` in `Core/Util.lua`).
- **`RoS-Tools.toc` load order is significant and manual.** Any new file must be
  added there in dependency order. `Core/Events.lua` must stay last — it fires
  the lifecycle and assumes every module has already registered.
- **`Data/GuildData.lua` is generated. Never hand-edit it.** Regenerate via the
  exporter. It is committed to the repo on purpose — it *is* the payload.
- **SavedVariables (`RoSToolsDB`) hold settings only.** The ilvl table is rebuilt
  from the static file on every `ADDON_LOADED`. Don't persist data there; 2.0
  removed exactly that anti-pattern.

## Architecture

Single addon namespace `ns`, passed as the second vararg to every file
(`local _, ns = ...`). No globals except `RoSToolsDB` and the slash-command
plumbing.

```
Core/Init.lua    ns.COLOR, ns.Print/Warn/Error/Debug, module registry
Core/Util.lua    RealmToSlug, MakeKey, NormalizeKey, DaysSince
Core/Config.lua  DEFAULTS, ILVL_COLORS, LoadConfig, SetOption
Core/Data.lua    ns.Data — Build() + read-only query API
Core/Events.lua  the one event frame; drives the lifecycle
Modules/*.lua    Tooltip, Roster, Browser, Commands
```

**Module lifecycle.** Modules are plain tables registered with
`ns:RegisterModule(name, tbl)`. They may define:

- `OnInitialize` — runs at `ADDON_LOADED`, after `LoadConfig()` and
  `Data:Build()`. SavedVariables are ready; game APIs may not be.
- `OnEnable` — runs at `PLAYER_LOGIN`. `ns.playerName` and
  `ns.playerRealmSlug` are set by then.

Dispatch is `pcall`-wrapped per module, so a broken module logs and the rest
still load. Keep it that way.

**Adding a module:** create `Modules/Foo.lua`, call `ns:RegisterModule("Foo", …)`,
add it to `RoS-Tools.toc` *above* `Core/Events.lua`.

## The realm slug problem

Every key is `Name-realm-slug`. In game we only get a display name
(`Moon Guard`) or a space-stripped tooltip form (`MoonGuard`), so
`Util.RealmToSlug` reconstructs the API slug locally. Two rules:

- Apostrophes are dropped **and suppress the word boundary** —
  `Kel'Thuzad` → `kelthuzad`, not `kel-thuzad`. This was the 1.x bug; those
  characters silently never resolved.
- CamelCase and letter↔digit transitions become hyphens —
  `WyrmrestAccord` → `wyrmrest-accord`, `Area52` → `area-52`.

Realms with lowercase joining words (`Sisters of Elune`) cannot be derived
mechanically and live in `SLUG_OVERRIDES` at the top of `Util.lua`. **When a
character's ilvl never resolves, check that table first.** `/ros set debug`
logs the failing key.

## Blizzard API surface — treat as unstable

- **Tooltips** use `TooltipDataProcessor.AddTooltipPostCall(Enum.TooltipDataType.Unit, …)`.
  A legacy `HookScript`/`hooksecurefunc` path is retained as a fallback only for
  clients lacking the modern API. Do not reintroduce the old hooks as the
  primary path — they fired on every tooltip in the game.
- **`Modules/Roster.lua`** touches the Communities UI, which breaks across
  patches. It searches for the name font string rather than assuming a widget
  path and no-ops when it can't find one. Preserve that defensiveness; never
  hard-code a widget path.
- Any new WoW global must be added to `read_globals` in `.luacheckrc` or lint
  fails.

## Conventions

- 2-space indent for Lua, 4 for Python (`.editorconfig`); LF endings, final
  newline, max line length 120.
- User-facing output goes through `ns.Print` / `ns.Warn` / `ns.Error`. Debug
  output through `ns.Debug`, which is a no-op unless `debug` is on.
- Colors come from `ns.COLOR` / `ns.Colorize`, not inline escape codes.
- New settings: add to `DEFAULTS` in `Config.lua` — `/ros set` and the
  README options table are both driven off it.

## Verifying changes

```powershell
luacheck .
```

That is the only automated check; there is no Lua test suite. CI runs the same
lint and then packages a zip excluding `.git*`, `build`, `Tools`, and `*.md`.

Behavioral changes must be verified in-game. Copy the folder to
`World of Warcraft\_retail_\Interface\AddOns\RoS-Tools` (the `.toc` sits directly
inside), then `/reload`.

## Regenerating the data

```powershell
$env:BLIZZARD_CLIENT_ID     = '<client id>'
$env:BLIZZARD_CLIENT_SECRET = '<client secret>'

python .\Tools\fetch_guild_info.py --realm khadgar --guild 'Riddle of Steel'
```

Overwrites `Data/GuildData.lua` in place. Credentials come from env vars only —
never commit them, and never add a secret to the addon side. 2.0 deleted an
embedded cipher plus a plaintext `ROSTOOLS_SECRET` that protected nothing; don't
bring that pattern back.

## Distribution scripts

`scripts/Install-RoSTools.ps1` and `scripts/Update-RoSToolsData.ps1` are handed
out as `irm … | iex` one-liners and must run on **Windows PowerShell 5.1** as
well as 7. That imposes four rules, all easy to break by accident:

- **No `param()` block and no `$PSScriptRoot`.** Piping into `iex` supplies
  neither. Every knob is an environment variable (`ROSTOOLS_ADDONS_PATH`,
  `ROSTOOLS_ADDON_PATH`, `ROSTOOLS_BRANCH`); add new ones the same way.
- **The whole body lives inside `& { … }`.** `iex` executes in the *caller's*
  scope, so an unwrapped script would leave `Set-StrictMode`,
  `$ErrorActionPreference = 'Stop'` and every helper function behind in the
  guildmate's console. Keep new code inside the block and use plain locals —
  `$script:` would leak for the same reason.
- **5.1 compatibility.** `Invoke-WebRequest` always needs `-UseBasicParsing`;
  TLS 1.2 is set explicitly because 5.1 can still negotiate 1.0. Document the
  one-liner as `irm`, never `iwr` — on 5.1 `iwr` routes through the IE parsing
  engine, which Windows 11 does not ship.
- **Self-contained.** They must not dot-source anything from the repo, so the
  `Test-GuildData` validator is duplicated from `Tools/Update-RoSTools.ps1` on
  purpose. Fix a validation bug in all three places.

Lint them with PSScriptAnalyzer before pushing; `PSAvoidUsingWriteHost` is
expected and ignored, since these are console-facing by design.

```powershell
Invoke-ScriptAnalyzer -Path .\scripts -Settings @{
    Rules = @{
        PSUseCompatibleSyntax  = @{ Enable = $true; TargetVersions = @('5.1', '7.0') }
        PSUseCompatibleCmdlets = @{ Enable = $true; compatibility = @('desktop-5.1.14393.206-windows') }
    }
}
```

They are served raw from `main`, so a bad push to those two files breaks
installs immediately — there is no release gate in front of them.
`scripts/Deploy-RoSTools.ps1` is unrelated: local dev-loop copy, never handed out.

## Versioning

`## Version:` in `RoS-Tools.toc` is the source of truth — CI greps it for the zip
name. Bump it and add a `CHANGELOG.md` entry in the same commit.
